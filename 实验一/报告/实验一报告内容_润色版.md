## 三、实验内容（2） 数据库设计及结构与数据维护

### 3.1 应用场景与关系设计

这次我选择做一个音乐歌单分享平台，主要想实现歌单整理、分享，以及寻找音乐口味相近的同好。用户可以把喜欢的歌曲整理成歌单，公开后供其他人浏览和收藏。除了分享歌单，我也想试着根据共同喜欢的歌曲计算用户之间的偏好相似度，看看哪些人的听歌口味比较接近。

数据库中需要保存用户、音乐人、专辑和歌曲的资料，也要记录歌单收录了哪些歌曲、用户喜欢哪些歌，以及收藏了哪些歌单。音乐人分为个人歌手和乐队，一首歌也可能由多位音乐人合作演唱。歌单可以设为公开或私密，里面的歌曲需要有排列顺序。用户喜欢歌曲的记录则用来计算偏好相似度。这次先把这些数据的存储、维护和查询做出来，实际播放音频的部分暂时不做。

我为这个平台单独创建了数据库 `music_platform`，所有者设为数据库用户 `jp`，九张业务表统一放在 `music` 模式下。具体的建库、建表语句和运行结果记录在下面。

用户与歌单为一对多关系；歌单与歌曲、用户与喜欢歌曲、用户与收藏歌单、歌曲与音乐人均为多对多关系，通过关联表实现。歌曲可关联一张专辑，也允许专辑为空。

| 表名 | 主要字段 | 关系与约束 |
|---|---|---|
| app_user | user_id、username、nickname、bio、created_at | user_id主键；username唯一；用户名与昵称非空 |
| artist | artist_id、artist_name、artist_type | 主键；类型限定solo/band |
| album | album_id、album_title、release_date、description | 主键；专辑名非空 |
| song | song_id、song_title、album_id、duration_seconds、genre | 主键；专辑外键；时长大于0；曲风默认Other |
| song_artist | song_id、artist_id | 复合主键；两个外键，支持合作演唱 |
| playlist | playlist_id、creator_id、playlist_name、description、visibility、created_at、cover_url | 主键；创建者外键；默认公开；公开/私密CHECK |
| playlist_song | playlist_id、song_id、position_no、added_at | 复合主键；两个外键；歌单内顺序唯一且大于0 |
| song_like | user_id、song_id、liked_at | 复合主键；两个外键，避免重复喜欢 |
| playlist_favorite | user_id、playlist_id、favorited_at | 复合主键；两个外键，避免重复收藏 |


主键保证实体标识唯一，外键维护参照完整性，NOT NULL、UNIQUE、DEFAULT与CHECK分别表达必填、唯一、默认值和取值规则。时间字段默认当前时间。歌曲、音乐人名称不设唯一，允许同名作品或艺人。公开字段及视图过滤用于展示规则，应用访问控制留待后续开发落实。

### 3.3 创建基本表及约束

接着创建 `music` 模式，用来存放业务表。建表也要注意顺序：先建用户、音乐人和专辑表，再建歌曲、歌单以及关联表，否则外键引用的表可能还不存在。主键、外键、非空、唯一、默认值和 CHECK 约束也在这一步一起设置。

```sql
CREATE SCHEMA music AUTHORIZATION jp;

CREATE TABLE music.app_user (
    user_id INTEGER PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    nickname VARCHAR(50) NOT NULL,
    bio VARCHAR(300),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_user_username UNIQUE (username)
);

CREATE TABLE music.artist (
    artist_id INTEGER PRIMARY KEY,
    artist_name VARCHAR(100) NOT NULL,
    artist_type VARCHAR(10) NOT NULL,
    CONSTRAINT ck_artist_type CHECK (artist_type IN ('solo', 'band'))
);

CREATE TABLE music.album (
    album_id INTEGER PRIMARY KEY,
    album_title VARCHAR(150) NOT NULL,
    release_date DATE,
    description VARCHAR(500)
);

CREATE TABLE music.song (
    song_id INTEGER PRIMARY KEY,
    song_title VARCHAR(150) NOT NULL,
    album_id INTEGER,
    duration_seconds INTEGER NOT NULL,
    genre VARCHAR(40) NOT NULL DEFAULT 'Other',
    CONSTRAINT fk_song_album FOREIGN KEY (album_id)
        REFERENCES music.album (album_id),
    CONSTRAINT ck_song_duration CHECK (duration_seconds > 0)
);

CREATE TABLE music.song_artist (
    song_id INTEGER NOT NULL,
    artist_id INTEGER NOT NULL,
    CONSTRAINT pk_song_artist PRIMARY KEY (song_id, artist_id),
    CONSTRAINT fk_sa_song FOREIGN KEY (song_id)
        REFERENCES music.song (song_id),
    CONSTRAINT fk_sa_artist FOREIGN KEY (artist_id)
        REFERENCES music.artist (artist_id)
);

  CREATE TABLE music.playlist (
      playlist_id INTEGER PRIMARY KEY,
      creator_id INTEGER NOT NULL,
      playlist_name VARCHAR(100) NOT NULL,
      description VARCHAR(500),
      visibility VARCHAR(10) NOT NULL DEFAULT 'public',
      created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
      CONSTRAINT fk_playlist_creator FOREIGN KEY (creator_id)
          REFERENCES music.app_user (user_id),
      CONSTRAINT ck_playlist_visibility CHECK (visibility IN ('public', 'private'))
  );

  CREATE TABLE music.playlist_song (
      playlist_id INTEGER NOT NULL,
      song_id INTEGER NOT NULL,
      position_no INTEGER NOT NULL,
      added_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
      CONSTRAINT pk_playlist_song PRIMARY KEY (playlist_id, song_id),
      CONSTRAINT uq_playlist_position UNIQUE (playlist_id, position_no),
      CONSTRAINT ck_playlist_position CHECK (position_no > 0),
      CONSTRAINT fk_ps_playlist FOREIGN KEY (playlist_id)
          REFERENCES music.playlist (playlist_id),
      CONSTRAINT fk_ps_song FOREIGN KEY (song_id)
          REFERENCES music.song (song_id)
  );

CREATE TABLE music.song_like (
    user_id INTEGER NOT NULL,
    song_id INTEGER NOT NULL,
    liked_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_song_like PRIMARY KEY (user_id, song_id),
    CONSTRAINT fk_sl_user FOREIGN KEY (user_id)
        REFERENCES music.app_user (user_id),
    CONSTRAINT fk_sl_song FOREIGN KEY (song_id)
        REFERENCES music.song (song_id)
);

CREATE TABLE music.playlist_favorite (
    user_id INTEGER NOT NULL,
    playlist_id INTEGER NOT NULL,
    favorited_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_playlist_favorite PRIMARY KEY (user_id, playlist_id),
    CONSTRAINT fk_pf_user FOREIGN KEY (user_id)
        REFERENCES music.app_user (user_id),
    CONSTRAINT fk_pf_playlist FOREIGN KEY (playlist_id)
        REFERENCES music.playlist (playlist_id)
);

SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema = 'music' AND table_type = 'BASE TABLE'
ORDER BY table_name;
```

### 3.4 修改表结构及管理索引

歌单除了名称和简介，也需要保存封面地址，所以我给歌单表增加了这个字段，同时把简介字段的长度扩大。之后在喜欢歌曲表的歌曲编号上创建一个普通索引，查到它的定义后再删除，看看删除后还会保留哪些索引，也借此区分普通索引和主键自动生成的索引。

```sql
ALTER TABLE music.playlist ADD COLUMN cover_url VARCHAR(300);
ALTER TABLE music.playlist ALTER COLUMN description TYPE VARCHAR(1000);


CREATE INDEX idx_song_like_song_id ON music.song_like (song_id);

SELECT schemaname, tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'music' AND indexname = 'idx_song_like_song_id';

DROP INDEX music.idx_song_like_song_id;

SELECT indexname
FROM pg_indexes
WHERE schemaname = 'music' AND tablename = 'song_like'
ORDER BY indexname;
```

## 四、实验内容（3） 查询、视图与偏好相似度

### 4.1 单表查询：搜索名称中含“音乐”的公开歌单。

先做一个简单的歌单搜索：查找名称中带有“音乐”的公开歌单，按歌单编号排序。这里只需要查询歌单表，用 WHERE 限定公开状态，再用 LIKE 匹配名称。

```sql
SELECT playlist_id, playlist_name, creator_id
FROM music.playlist
WHERE visibility = 'public' AND playlist_name LIKE '%音乐%'
ORDER BY playlist_id;
```

### 4.2 多表连接并排序：歌单1的歌曲、专辑及音乐人。

查看歌单详情时，只查歌单表就不够了，还需要知道里面有哪些歌、属于哪张专辑、由谁演唱。所以这里连接歌单、收录关系、歌曲、专辑和音乐人相关表，再按歌曲在歌单中的顺序排列。没有关联专辑的歌曲用左连接保留下来，合作歌曲则分别列出演唱者。

```sql
SELECT ps.position_no, s.song_title,
       COALESCE(al.album_title, '未关联专辑') AS album_title,
       ar.artist_name
FROM music.playlist p
JOIN music.playlist_song ps ON ps.playlist_id = p.playlist_id
JOIN music.song s ON s.song_id = ps.song_id
LEFT JOIN music.album al ON al.album_id = s.album_id
JOIN music.song_artist sa ON sa.song_id = s.song_id
JOIN music.artist ar ON ar.artist_id = sa.artist_id
WHERE p.playlist_id = 1 AND p.visibility = 'public'
ORDER BY ps.position_no, ar.artist_id;
```

### 4.3 聚集函数：歌单1的歌曲数量、总时长和平均时长。

这里用 COUNT、SUM 和 AVG 统计歌单1有多少首歌、总时长是多少，以及平均每首歌的时长，平均值保留两位小数。需要注意的是，这次只连接收录关系和歌曲表。如果把音乐人也连接进来，合作歌曲就可能被重复统计。

```sql
SELECT COUNT(*) AS song_count,
       SUM(s.duration_seconds) AS total_seconds,
       ROUND(AVG(s.duration_seconds), 2) AS avg_seconds
FROM music.playlist_song ps
JOIN music.song s ON s.song_id = ps.song_id
WHERE ps.playlist_id = 1;
```

### 4.4 分组查询：收藏人数至少为2的公开歌单。

接着统计公开歌单的收藏人数，只显示至少有2人收藏的歌单。先按歌单分组，再用 HAVING 筛选，结果按收藏人数从多到少排列；人数相同的，按歌单编号排序。这样可以简单看一下哪些歌单比较受欢迎。

```sql
SELECT p.playlist_id, p.playlist_name, COUNT(f.user_id) AS favorite_count
FROM music.playlist p
LEFT JOIN music.playlist_favorite f ON f.playlist_id = p.playlist_id
WHERE p.visibility = 'public'
GROUP BY p.playlist_id, p.playlist_name
HAVING COUNT(f.user_id) >= 2
ORDER BY favorite_count DESC, p.playlist_id;
```

### 4.5 嵌套查询：用户2喜欢而用户1尚未喜欢的歌曲。

如果用户1想从用户2喜欢的歌里找一些自己还没喜欢过的歌，就可以用这个嵌套查询。先用 IN 找到用户2喜欢的歌曲，再用 NOT EXISTS 排除用户1已经喜欢的部分，剩下的就可以作为推荐候选。

```sql
SELECT s.song_id, s.song_title
FROM music.song s
WHERE s.song_id IN (
    SELECT song_id FROM music.song_like WHERE user_id = 2
)
AND NOT EXISTS (
    SELECT 1 FROM music.song_like mine
    WHERE mine.user_id = 1 AND mine.song_id = s.song_id
)
ORDER BY s.song_id;
```

### 4.6 创建并使用视图：公开歌单、创建者和歌曲数。

公开歌单列表需要一起显示歌单名称、创建者昵称和歌曲数量，每次都写一遍连接和统计有些重复，所以我把这部分查询做成了视图 `music.v_public_playlist`。视图只显示公开歌单，同时用左连接保留空歌单。创建后直接查询视图，检查结果是否符合预期。

```sql
CREATE VIEW music.v_public_playlist AS
SELECT p.playlist_id, p.playlist_name, u.nickname AS creator,
       COUNT(ps.song_id) AS song_count
FROM music.playlist p
JOIN music.app_user u ON u.user_id = p.creator_id
LEFT JOIN music.playlist_song ps ON ps.playlist_id = p.playlist_id
WHERE p.visibility = 'public'
GROUP BY p.playlist_id, p.playlist_name, u.nickname;

SELECT playlist_id, playlist_name, creator, song_count
FROM music.v_public_playlist
ORDER BY playlist_id;
```

### 4.7 特色扩展：用户1与其余用户的喜欢歌曲 Jaccard 相似度。

做完基础查询后，我还想试一下：能不能从喜欢歌曲的重合程度，看出哪些用户的音乐口味比较接近？这里以用户1为参照，统计每个人喜欢的歌曲数，以及和用户1共同喜欢的歌曲数，再计算 Jaccard 相似度并排序，作为之后寻找音乐同好的基础。不过，没有喜欢记录的用户不能直接算作口味不同，所以这部分返回 NULL。

```sql
WITH like_counts AS (
    SELECT user_id, COUNT(*) AS liked_count
    FROM music.song_like GROUP BY user_id
), common_counts AS (
    SELECT other.user_id, COUNT(*) AS common_count
    FROM music.song_like mine
    JOIN music.song_like other ON other.song_id = mine.song_id
    WHERE mine.user_id = 1 AND other.user_id <> 1
    GROUP BY other.user_id
)
SELECT u.user_id, u.nickname,
       COALESCE(lc.liked_count, 0) AS liked_count,
       COALESCE(cc.common_count, 0) AS common_count,
       CASE WHEN COALESCE(lc.liked_count, 0) = 0
                  OR COALESCE(me.liked_count, 0) = 0 THEN NULL
            ELSE ROUND(100.0 * COALESCE(cc.common_count, 0) /
                 NULLIF(me.liked_count + lc.liked_count -
                        COALESCE(cc.common_count, 0), 0), 2)
       END AS similarity_pct
FROM music.app_user u
LEFT JOIN like_counts lc ON lc.user_id = u.user_id
LEFT JOIN like_counts me ON me.user_id = 1
LEFT JOIN common_counts cc ON cc.user_id = u.user_id
WHERE u.user_id <> 1
ORDER BY similarity_pct DESC NULLS LAST, u.user_id;
```

图 34：特色扩展（截图34）：用户1与其余用户的喜欢歌曲 Jaccard 相似度。

采用共同喜欢数 / 喜欢歌曲集合并集大小计算Jaccard相似度。用户2为60%，用户5为40%，用户3、4为0%，用户6为NULL（截图显示空白）。NULL表示缺少偏好数据，与有数据但无交集的0%不同。

## 五、实验总结

这次实验从部署数据库开始，一直到建表、维护数据和查询，算是把关系模型、多对多关联、实体完整性和参照完整性用在了一个具体的场景里。连接、聚集、分组、嵌套查询和视图也都有了对应的用途。其中我比较需要注意的是，一首歌不一定只对应一条演唱关系，统计时不能直接把连接后的行数当成歌曲数。另外，没有专辑的歌曲和空歌单需要用 LEFT JOIN 保留，NULL 和零值也要区分清楚。

不过部署过程并没有那么顺利。clusterconfig.xml 中有两处主机名缺少结束双引号，导致 XML 解析失败。排查时，我又在 script 目录下用相对路径编辑，结果误建了一个同名配置文件，安装程序真正读取的上一级配置根本没有改到，所以改完还是报错。后来核对绝对路径，并查看文件里的实际字符，才发现原文件中缺失的引号和不换行空格，处理后安装成功。这个问题也提醒我，排查配置时不能只看文件名，还得确认自己改的到底是不是程序读取的那个文件。（警钟敲响）

修改表结构时还遇到了 Session unused timeout 和 Broken pipe。我重新连接后，先检查目标字段的状态，再继续操作，最后完成了修改。以后执行前还是要确认当前用户、数据库和对象路径；连接中断后，也应该先查一下刚才的操作有没有生效，并及时保存 SQL 和运行结果。目前完成的是平台的数据库部分，歌单界面、分享时的访问控制，以及同好推荐，还需要在后续开发中继续实现。
